# WalimApp — Decision Register

- **Status:** Baseline v1.0 (Phase 0)
- **Last Updated:** 2026-10-29
- **Purpose:** Single source of truth for (1) **Confirmed Architectural Decisions (`ADR-*`)** and (2) **Unresolved Product & Business Questions (`DEC-*`)** with provisional defaults and the exact delivery phase by which each must be resolved.

---

## Part 1: Confirmed Architectural Decisions (`ADR-001` .. `ADR-015`)

| ID | Decision Title | Confirmed Choice | Rationale & Source Traceability |
| :--- | :--- | :--- | :--- |
| **`ADR-001`** | **Shared Android & Windows Owner Codebase** | One Flutter codebase (`apps/owner`) targeting both Android (`API 24+`) and Windows (`x64`), sharing ~90% of code (domain, Drift SQLite, outbox sync, auth, PDF, l10n) with adaptive layouts (`< 600dp` touch vs `>= 600dp` desktop) and 5 thin platform adapters. | Eliminates duplicate mobile/desktop business logic for a solo developer while serving phone-first Algerian venue owners and office PC receptionists (`TR-14`). |
| **`ADR-002`** | **Single Laravel 12 Modular Monolith Backend** | PHP 8.4 + Laravel 12.x modular monolith serving REST/Sync API (`/api/v1/*`), SSR Public Marketplace (`Blade + Tailwind + Alpine`), and Super-Admin (`Filament v4`). | One deployable repository and runtime; avoids microservices, Kubernetes, or separate Node.js SSR servers (`TR-12`, `TR-13`). |
| **`ADR-003`** | **PostgreSQL 17 with Database-Backed Infrastructure** | PostgreSQL 17 (`btree_gist`, `pg_trgm`) as the sole required server datastore, powering relational tables, slot exclusion constraints, full-text/trigram search, Laravel jobs queue, cache, and locks. | Avoids mandatory Redis, Meilisearch, or Kafka in Phases 2–3 while providing engine-level booking guarantees (`TR-05`, `TR-13`). |
| **`ADR-004`** | **Client/App-Generated UUIDv7 Primary Keys** | All syncable entities use RFC 9562 UUIDv7 generated in Dart (`uuid`) and PHP (`Ramsey\Uuid`). | Time-ordered B-tree locality without offline ID collisions or dependence on PostgreSQL 18's server-only `uuidv7()` (`TR-07`, `TR-12`). |
| **`ADR-005`** | **69-Wilaya Data-Driven Reference Schema** | `wilayas` (`code VARCHAR(2)` `'01'`..`'69'`) and `communes` tables are data-driven and seeded with all **69 official Algerian Wilayas** in Arabic and French. | Corrects the outdated 58-Wilaya assumption in `architecture-gemini-argon.md` and supports Algeria's 69-Wilaya administrative structure (`TR-01`). |
| **`ADR-006`** | **Strict Separation of `booking_requests` and `reservations`** | Public marketplace inquiries are stored exclusively in `booking_requests` (`pending`, `approved`, `rejected`, `expired`, `cancelled_by_requester`) and never block slots until an owner approves them in an atomic transaction creating a `reservations` row. | Prevents unverified web visitors from locking a venue's calendar and cleanly separates leads from binding contracts (`TR-02`, `TR-03`). |
| **`ADR-007`** | **Orthogonal Client `pending_sync` Overlay** | `reservations.status` holds only domain statuses (`confirmed`, `tentative`, `cancelled`, `needs_review`). Client sync state (`has_pending_sync`) is derived from unacknowledged `sync_outbox` rows. | Allows an already-confirmed reservation edited offline to remain `confirmed` while visibly awaiting sync acknowledgement (`TR-04`). |
| **`ADR-008`** | **Configurable Hall Slots & `btree_gist` Exclusion** | Venues define custom `hall_slots` (including overnight ranges where `spans_next_day = true`). `reservations` stores concrete `[starts_at_local, ends_at_local)` timestamps guarded in PostgreSQL by an `EXCLUDE USING gist` constraint where `status IN ('confirmed', 'tentative') AND deleted_at IS NULL`. | Guarantees zero double-bookings across arbitrary slot definitions without denormalized boolean flag drift (`TR-05`). |
| **`ADR-009`** | **Append-Only Immutable Financial Ledger** | `payments` rows are append-only (`deposit`, `installment`, `final_settlement`, `refund`, `adjustment`) enforced by SQLite and PostgreSQL triggers preventing `UPDATE`/`DELETE`. All amounts are integer `DZD` (`BIGINT`). | Protects financial history against silent tampering or duplicate sync overwrites (`TR-09`). |
| **`ADR-010`** | **Idempotent Outbox Push & Cursor Delta Pull** | Every client mutation carries a UUIDv7 `operation_id` recorded in `sync_processed_operations`; server delta pulls use monotonically increasing `sync_change_log.seq`. | Safe retries over unstable 3G/4G/ADSL connections and deterministic multi-device convergence (`TR-06`). |
| **`ADR-011`** | **Non-Destructive Staged Local-to-Connect Migration** | Local-to-Connect migration creates a `.walimbak` backup, uploads chunks to `migration_staging_records`, validates FKs/overlaps/financial checksums on the server, and promotes in a single transaction before switching local mode. | Protects local SQLite data if migration is interrupted by power or network failure (`TR-07`). |
| **`ADR-012`** | **Ed25519 Perpetual Local License & Safe Connect Expiry** | WalimApp Local uses offline-verifiable Ed25519 `.walimlic` files where `updates_until` only gates builds compiled after that date. Connect subscription expiry pauses cloud sync/marketplace while preserving full offline local usage. | Honors the perpetual license promise and guarantees zero data lockout (`TR-08`). |
| **`ADR-013`** | **Individual Authenticated Users & Venue-Scoped RBAC** | In WalimApp Connect, each employee authenticates with their own user account on their own Android/Windows device and is authorized per venue (`venue_memberships`), with server-side filtering of financial data. | Supports multi-user venue teams on phones and desktops without sharing a single owner password (`TR-10`, `TR-15`). |
| **`ADR-014`** | **Bilingual `ar-DZ` (RTL) / `fr-DZ` (LTR) with Western Digits** | All interfaces and PDFs support Arabic and French from Phase 1, enforcing Western Arabic digits (`0-9`) and integer Dinar (`DZD` / `د.ج`). | Matches standard Algerian commercial and legal practice. |
| **`ADR-015`** | **Phase 4 Isolation for Virtual Tours & Provider Portal** | 360° virtual tours (`Pannellum` on S3/R2) and provider self-service registration are deferred to Phase 4 while reserving lightweight schema hooks. | Prevents high-bandwidth media and secondary portals from delaying Phases 1–3. |

## Part 2: Unresolved Product & Operational Decisions (`DEC-01` .. `DEC-16`)

To keep engineering moving without inventing hidden business rules, every unresolved question below has a **Provisional Default** and a hard **Resolution Gate**.

### 2.1 Must Be Resolved Before Phase 1 Implementation (`WalimApp Local MVP`)

| ID | Question Requiring Product Owner Decision | Options | Provisional Default (Used Unless Overridden) | Resolution Gate |
| :--- | :--- | :--- | :--- | :--- |
| **`DEC-01`** | **Phase 1 Target Release Packaging (Android vs. Windows Priority):** Should Phase 1 ship Android APK/AAB and Windows `.msix`/`.exe` simultaneously from the shared codebase, or validate the touch workflow on Android first followed immediately by the Windows build in the same phase? | **A)** Ship both Android and Windows installers at the Phase 1 gate from the shared codebase.<br>**B)** Release Android build in Sprint 1.3 for phone-first owners, then Windows desktop layout/installer in Sprint 1.4 before closing Phase 1. | **Option A/B hybrid:** Develop all Phase 1 slices in the shared Flutter codebase testing on both Android and Windows; prioritize phone-first touch ergonomics in early sprints so Android is testable immediately, and require **both** Android and Windows builds to pass acceptance before closing Phase 1. | **Before Phase 1 Sprint 1** |
| **`DEC-02`** | **Multi-Hall vs. Multi-Venue Scope in WalimApp Local:** Does a single WalimApp Local perpetual license allow 1 physical venue containing multiple bookable halls/spaces (e.g., *Salle Hommes*, *Salle Femmes*, *Jardin*), or multiple separate physical venues? | **A)** 1 physical venue with up to `N` halls/spaces (default `N = 5`) per Local license.<br>**B)** Unlimited physical venues in Local mode. | **Option A:** 1 physical venue with multiple bookable halls/spaces (up to 5 halls by default, configurable in `.walimlic`). Multi-venue management across distinct addresses is a Connect / multi-license feature. | **Before Phase 1 Sprint 1** |
| **`DEC-03`** | **Tentative Hold (`Option`) Expiry Behavior:** When an owner creates a `tentative` booking hold with a `hold_expires_at` date and the date passes without a deposit, what should happen? | **A)** Flag visibly as *"Hold Expired — Action Required"* on the calendar and dashboard, keeping the slot blocked until the owner explicitly confirms or cancels.<br>**B)** Automatically cancel the tentative hold and free the slot without owner action. | **Option A:** Never auto-cancel silently. Flag expired holds prominently so the owner can call the customer before releasing the date. | **Before Phase 1 Sprint 2** |
| **`DEC-04`** | **Local-Mode Staff Profiles / PINs on a Shared Device:** In WalimApp Local (single device, no cloud), does the owner need a local-only Receptionist mode (hiding total annual revenue/profit behind an Owner PIN on that PC/phone)? | **A)** Yes, include local Owner vs. Receptionist PIN switch on the device.<br>**B)** No, Local mode is single-owner; role permissions exist only in WalimApp Connect. | **Option A:** Support a simple local Owner PIN lock for sensitive financial reports and settings, reusing the same permission matrix used by Connect roles. | **Before Phase 1 Sprint 2** |
| **`DEC-05`** | **Default Printed Contract & Receipt Layout:** Should generated PDF contracts and payment receipts be single-language (selected per document: Arabic or French) or side-by-side bilingual on the same page? | **A)** User selects document language (`Arabic`, `French`, or `Bilingual Header + Selected Body`) at print/share time.<br>**B)** Strictly separate Arabic and French templates. | **Option A:** Provide clean Arabic (RTL) and French (LTR) templates with a bilingual venue header, selectable per printout/WhatsApp share. | **Before Phase 1 Sprint 3** |
| **`DEC-06`** | **Local Backup Encryption Key Recovery:** How should `.walimbak` local backups be encrypted so an owner does not lose their data if their PC/phone dies and they forgot a custom password? | **A)** Encrypt using a deterministic key derived from the owner's **License Key (`license_id` + activation code)**, optionally combined with a user passphrase.<br>**B)** Require a mandatory user-invented backup password only. | **Option A:** Default encryption key is derived via Argon2id/HKDF from the owner's License Key (which Super-Admin can always re-provide after verifying identity), with an optional secondary passphrase. | **Before Phase 1 Sprint 4** |

### 2.3 Must Be Resolved Before Phase 3 Implementation (`Public Marketplace`)

| ID | Question Requiring Product Owner Decision | Options | Provisional Default (Used Unless Overridden) | Resolution Gate |
| :--- | :--- | :--- | :--- | :--- |
| **`DEC-12`** | **Public Phone/WhatsApp Verification on Booking Requests:** Must a public visitor verify their phone number via SMS OTP before submitting a `booking_request`, or use free anti-spam controls? | **A)** Cloudflare Turnstile + IP/phone rate-limiting + honeypot by default (zero SMS cost per inquiry), with optional OTP toggle.<br>**B)** Mandatory SMS OTP on every public booking request. | **Option A:** Turnstile + strict rate-limiting + honeypot by default so per-SMS fees in Algeria do not drain platform margins or block families when SMS gateways lag. | **Before Phase 3 Sprint 1** |
