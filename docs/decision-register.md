## Part 1: Confirmed Architectural Decisions (`ADR-001` .. `ADR-015`)

| ID | Decision Title | Confirmed Choice | Rationale & Traceability (`docs/architecture-review.md`) |
| :--- | :--- | :--- | :--- |
| **`ADR-001`** | **Shared Android & Windows Owner Codebase & Edition Boundary** | One Flutter codebase (`apps/owner`, current stable Flutter SDK pinned at Sprint 1.1 start) targeting both Android (`API 24+`) and Windows (`x64`), sharing ~90% of code with adaptive layouts (`< 600dp` touch vs `>= 600dp` desktop) and 5 thin platform adapters. **Phase 1 (`Local`) is a single-device offline edition; Phase 2 (`Connect`) delivers the shared multi-user calendar across phones and PCs.** | Eliminates duplicate mobile/desktop business logic for a solo developer while setting honest expectations between single-device Local and multi-device Connect (`TR-02`). |
| **`ADR-002`** | **Single Laravel Modular Monolith & Verified Phase 2 Stack Matrix** | Single PHP 8.4 + Laravel modular monolith serving REST/Sync API (`/api/v1/*`), SSR Public Marketplace (`Blade + Tailwind CSS + Alpine.js`), and Super-Admin (`Filament`). Both **Track 1 (`Laravel 13.x + Filament v5.x + Livewire v4.x + Tailwind v4.1+`, recommended because Laravel 13 has security support until March 2028 whereas Laravel 12 ends Feb 2027)** and **Track 2 (`Laravel 12.x + Filament v4.x + Livewire v3.x`)** are verified via `composer update --dry-run` (`110 installs, 0 conflicts`) and locked at the Phase 2 Sprint 2.1 gate. | One deployable repository and runtime; avoids microservices, Kubernetes, or unverified package constraints (`TR-01`, `TR-13`). |
| **`ADR-003`** | **PostgreSQL 17 on Server & SQLCipher Encryption at Rest on Client** | PostgreSQL 17 (`btree_gist`, `pg_trgm`) as the sole required server datastore (powering relational tables, slot exclusion constraints, search, queues, cache, and locks), paired with **SQLCipher (`sqlcipher_flutter_libs` + `drift`, `AES-256`)** on Android and Windows for local database encryption at rest (`NFR-04`). | Avoids mandatory Redis/Meilisearch on the server while guaranteeing true local encryption at rest on client devices (`TR-03`, `TR-08`). |
| **`ADR-004`** | **Client/App-Generated UUIDv7 Primary Keys** | All syncable entities use RFC 9562 UUIDv7 generated in Dart (`uuid`) and PHP (`Ramsey\Uuid`). | Time-ordered B-tree locality without offline ID collisions or dependence on PostgreSQL 18's server-only `uuidv7()` (`TR-05`). |
| **`ADR-005`** | **Authoritative 69-Wilaya Data-Driven Reference Schema** | `wilayas` (`code VARCHAR(2)` `'01'`..`'69'`) and `communes` (1,541 communes) are seeded from a versioned, checksummed dataset verified against official Algerian *Journal Officiel (JORADP)* / ONS listings in Arabic and French. | Corrects the outdated 58-Wilaya assumption in `architecture-gemini-argon.md` and proves completeness via automated count/checksum tests (`TR-12`). |
| **`ADR-006`** | **Strict Separation of `booking_requests` and `reservations`** | Public marketplace inquiries are stored exclusively in `booking_requests` (`pending`, `approved`, `rejected`, `expired`, `cancelled_by_requester`) and never block slots until an owner approves them in an atomic transaction creating a `reservations` row. | Prevents unverified web visitors from locking a venue's calendar and cleanly separates leads from binding contracts (`TR-06`). |
| **`ADR-007`** | **Orthogonal Client `pending_sync` Overlay** | `reservations.status` holds only domain statuses (`confirmed`, `tentative`, `cancelled`, `needs_review`). Client sync state (`has_pending_sync`) is derived from unacknowledged `sync_outbox` rows. | Allows an already-confirmed reservation edited offline to remain `confirmed` while visibly awaiting sync acknowledgement (`TR-07`). |
| **`ADR-008`** | **Configurable Hall Slots & `btree_gist` Exclusion** | Venues define custom `hall_slots` (including overnight ranges where `spans_next_day = true`). `reservations` stores concrete `[starts_at_local, ends_at_local)` timestamps guarded in PostgreSQL by an `EXCLUDE USING gist` constraint where `status IN ('confirmed', 'tentative') AND deleted_at IS NULL`. | Guarantees zero double-bookings across arbitrary slot definitions without denormalized boolean flag drift (`TR-08`). |
| **`ADR-009`** | **Canonical Integer Whole-DZD Money & Unconditionally Append-Only `payments`** | All monetary values across all tables, DTOs, checksums, and PDFs are **integer whole Algerian Dinars (`BIGINT` `DZD`, column suffix `*_dzd`)**. Recorded `payments` rows are protected by SQLite and PostgreSQL `BEFORE UPDATE OR DELETE` triggers that **unconditionally reject all `UPDATE` and `DELETE` operations on every column**; corrections require inserting a `refund` or `adjustment` row referencing `parent_payment_id` with a mandatory `reason`. | Eliminates 100x centime/Dinar conversion bugs and prevents any post-hoc tampering with recorded payments (`TR-10`). |
| **`ADR-010`** | **Monotonic `outbox_seq` Push, Commit-Locked Venue Cursor & `permissions_hash` Reset** | Client mutations queue in `sync_outbox` ordered by monotonic `outbox_seq` with parent-before-child dependency blocking (`depends_on_outbox_seq`). Server delta pulls use per-venue `venue_sync_state.last_seq` locked with `SELECT ... FOR UPDATE` at transaction commit, plus `permissions_hash` cursor reset on role upgrade/downgrade and `is_financial_masked` protection on masked rows. | Immune to client clock skew, prevents out-of-order commits from slipping behind pull cursors, and safely handles employee role changes (`TR-09`). |
| **`ADR-011`** | **Non-Destructive Staged Local-to-Connect Migration (Including Documents)** | Local-to-Connect migration creates a WAL-safe `.walimbak` backup, uploads all 11 relational entity types (including `contract_templates` and `generated_documents` metadata) to `migration_staging_records`, transfers PDF/media binaries to staging S3/R2 verified by `sha256_checksum`, validates counts/FKs/overlaps/financial checksums on the server, and promotes in a single transaction before switching local mode. | Guarantees 100% preservation of customers, bookings, finances, contract templates, and generated PDFs with safe interruption recovery (`TR-05`). |
| **`ADR-012`** | **Ed25519 Perpetual Local License, Phase 1 Offline Issuer CLI & Safe Connect Expiry** | WalimApp Local uses offline-verifiable Ed25519 `.walimlic` files signed in Phase 1 via a standalone operator CLI (`tools/license-issuer`, external private key, `issued-licenses.jsonl` ledger imported into Admin in Phase 2). `updates_until` only gates builds compiled after that date. Connect expiry falls back to local offline mode and reconciles `sync_outbox` upon renewal. | Provides a complete, secure Phase 1 license issuance workflow and honors perpetual/offline guarantees (`TR-04`). |
| **`ADR-013`** | **Individual Authenticated Users, Venue RBAC & Realistic Revocation Bounds** | Each Connect user authenticates with their own account on their own device (`venue_memberships`). Revocation blocks online calls immediately (`403`/`401`), purges cached venue data on next reconnection, bounds offline staff access via a 72-hour `OfflineAccessLease`, and sends zero PII in FCM push pokes. | Enforces multi-tenant security and realistic offline revocation semantics without sharing a single owner password (`TR-11`). |
| **`ADR-014`** | **Bilingual `ar-DZ` (RTL) / `fr-DZ` (LTR) with Western Digits** | All interfaces and PDFs support Arabic and French from Phase 1, enforcing Western Arabic digits (`0-9`) and integer whole Dinar (`DZD` / `د.ج`). | Matches standard Algerian commercial and legal practice (`TR-12`). |
| **`ADR-015`** | **Phase 4 Isolation for Virtual Tours & Provider Portal** | 360° virtual tours (`Pannellum` on S3/R2) and provider self-service registration are deferred to Phase 4 while reserving lightweight schema hooks. | Prevents high-bandwidth media and secondary portals from delaying Phases 1–3 (`TR-14`). |

| ID | Question Requiring Product Owner Decision | Options & Trade-Offs | Recommended Default (Subject to PO Approval) | Resolution Gate |
| :--- | :--- | :--- | :--- | :--- |
| **`DEC-01`** | **Phase 1 Single-Device Local vs. Phase 2 Shared Multi-User Calendar Priority:** Phase 1 (`WalimApp Local`) is a **single-device offline edition** (running on one Android phone OR one Windows PC without cross-device sync), while Phase 2 (`WalimApp Connect`) delivers the **shared multi-user calendar across multiple phones and Windows PCs**. How should we sequence Phase 1 and Phase 2? | **A)** Complete all 4 sprints of Phase 1 (`WalimApp Local` on Android + Windows, including offline PDF contracts, `.walimbak` backups, and offline `.walimlic` licensing) before starting Phase 2 (`Connect`).<br>**B)** Deliver Phase 1 Sprints 1.1–1.3 as a single-device pilot, and if immediate multi-phone family/team calendar sharing is the top business priority, pull the Phase 2 Connect sync slice forward immediately after Phase 1 core acceptance. | **Option A (with clear positioning):** Build Phase 1 in the shared Android + Windows Flutter codebase (`apps/owner`), deliver the single-device Android pilot in Sprint 1.3 and full Android + Windows Local MVP in Sprint 1.4, and clearly label Phase 2 (`Connect`) as the release that delivers multi-user shared calendar sync across devices. | **Before Phase 1 Sprint 1.1** |
| **`DEC-02`** | **Multi-Hall vs. Multi-Venue Scope in WalimApp Local:** Does a single WalimApp Local perpetual license allow 1 physical venue containing multiple bookable halls/spaces (e.g., *Salle Hommes*, *Salle Femmes*, *Jardin*), or multiple separate physical venues? | **A)** 1 physical venue with up to `max_halls` bookable halls/spaces (default `max_halls = 5`, encoded in `.walimlic`) per Local license.<br>**B)** Unlimited physical venues in Local mode. | **Option A:** 1 physical venue with multiple bookable halls/spaces (default up to 5 halls, configurable per `.walimlic`). Multi-venue management across distinct addresses is a WalimApp Connect / multi-license feature. | **Before Phase 1 Sprint 1.1** |
| **`DEC-03`** | **Tentative Hold (`Option`) Expiry Behavior:** When an owner creates a `tentative` booking hold with a `hold_expires_at` date and the date passes without a deposit, what should happen? | **A)** Flag visibly as *"Hold Expired — Action Required"* on the calendar and dashboard, keeping the slot blocked until the owner explicitly confirms or cancels.<br>**B)** Automatically cancel the tentative hold and free the slot without owner action. | **Option A:** Never auto-cancel silently. Flag expired holds prominently so the owner can call the customer before releasing the date. | **Before Phase 1 Sprint 1.2** |
| **`DEC-04`** | **Local-Mode Staff Profiles / PIN on a Single Shared Device:** In WalimApp Local (single device, no cloud), does the owner need a local Owner PIN to lock sensitive annual revenue/profit reports and settings when a receptionist uses that same PC/phone? | **A)** Yes, include a local Owner PIN lock for sensitive financial reports, backup/restore, and venue settings (note: the SQLite database itself is encrypted at rest via SQLCipher).<br>**B)** No, Local mode has no local PIN screen lock; role restrictions exist only in WalimApp Connect. | **Option A:** Support an optional local Owner PIN lock for sensitive financial summary screens and settings on a shared single device, reusing the same UI permission matrix used by Connect roles. | **Before Phase 1 Sprint 1.2** |
| **`DEC-05`** | **Default Printed Contract & Receipt Layout:** Should generated PDF contracts and payment receipts be single-language (selected per document: Arabic or French) or side-by-side bilingual on the same page? | **A)** User selects document language (`Arabic RTL`, `French LTR`, or `Bilingual Venue Header + Selected Body`) at print/share time.<br>**B)** Strictly separate Arabic-only and French-only templates. | **Option A:** Provide clean Arabic (RTL) and French (LTR) templates with a bilingual venue header, selectable per printout/WhatsApp share. | **Before Phase 1 Sprint 1.3** |
| **`DEC-06`** | **`.walimbak` Backup Key Management & Recovery Model (`P0-1` — OPEN FOR EXPLICIT PO CHOICE):** Every `.walimbak` archive is encrypted with a fresh random 256-bit `AES-256-GCM` Data Encryption Key (DEK) that is **strictly separated from the WalimApp license key**. How should that DEK be wrapped for recovery if the owner's device is lost or destroyed? | **Option A (Zero-Knowledge Owner Custody — Passphrase + Printable 256-bit Recovery Key):** During backup setup, the app generates a high-entropy random 256-bit **Recovery Key** (rendered as a printable PDF *"Emergency Recovery Sheet"* for the owner's physical safe) AND lets the owner set a **Backup Passphrase** (`Argon2id`, `m=64 MiB, t=3, p=1`). The DEK is wrapped in 2 slots so *either* the Passphrase *or* the Recovery Sheet can decrypt `.walimbak`. **Who can decrypt:** Only the owner. **Consequence:** WalimApp Support can **never** decrypt backups; if the owner loses *both* their passphrase and their printed Recovery Sheet, off-device `.walimbak` files are permanently unrecoverable.<br><br>**Option B (Opt-In Asymmetric Support Escrow Envelope):** Same as Option A, plus—*only if the owner explicitly opts in and signs a consent notice*—a 3rd DEK wrapper slot encrypted with an offline vendor `X25519` Backup Escrow Public Key (independent of the Ed25519 license key, with the private key held offline in split-knowledge custody by WalimApp). **Who can decrypt:** The owner, OR WalimApp Support after identity verification. **Consequence:** Allows support recovery if the owner loses both credentials, but creates vendor key-custody risk and Law 18-07 data-processor obligations. | **OPEN — Recommended Choice: Option A (Zero-Knowledge Owner Custody via Passphrase + Printable 256-bit Recovery Sheet)** unless the Product Owner explicitly chooses to offer Option B's opt-in support escrow and accept key-custody operations. Must be explicitly approved before implementing `.walimbak` encryption in Sprint 1.4. | **Before Phase 1 Sprint 1.4** |
