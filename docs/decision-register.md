## Part 1: Confirmed Architectural Decisions (`ADR-001` .. `ADR-015`)

| ID | Decision Title | Confirmed Choice | Rationale & Traceability (`docs/architecture-review.md`) |
| :--- | :--- | :--- | :--- |
| **`ADR-001`** | **Shared Android & Windows Owner Codebase & Edition Boundary** | One Flutter codebase (`apps/owner`, current stable Flutter SDK pinned at Sprint 1.1 start) targeting both Android (`API 24+`) and Windows (`x64`), sharing ~90% of code with adaptive layouts (`< 600dp` touch vs `>= 600dp` desktop) and 5 thin platform adapters. **`WalimApp Local` is a single-device offline edition; `WalimApp Connect` delivers the shared multi-user calendar across phones and PCs.** | Eliminates duplicate mobile/desktop business logic for a solo developer while setting honest expectations between single-device Local and multi-device Connect (`TR-02`). |
| **`ADR-002`** | **Single Laravel Modular Monolith & Verified Backend Stack Matrix** | Single PHP 8.4 + Laravel modular monolith serving REST/Sync API (`/api/v1/*`), SSR Public Marketplace (`Blade + Tailwind CSS + Alpine.js`), and Super-Admin (`Filament`). Both **Track 1 (`Laravel 13.x + Filament v5.x + Livewire v4.x + Tailwind v4.1+`, recommended because Laravel 13 has security support until March 2028 whereas Laravel 12 ends Feb 2027)** and **Track 2 (`Laravel 12.x + Filament v4.x + Livewire v3.x`)** are verified via `composer update --dry-run` (`110 installs, 0 conflicts`) and locked at the Sprint 2.1 gate. | One deployable repository and runtime; avoids microservices, Kubernetes, or unverified package constraints (`TR-01`, `TR-13`). |
| **`ADR-003`** | **PostgreSQL 17 on Server & Explicit `sqlite3mc` (`chacha20`) Fail-Closed Encryption on Client** | PostgreSQL 17 (`btree_gist`, `pg_trgm`) as the sole required server datastore, paired on Android and Windows with **`drift` (`^2.35.0`) + `sqlite3` (`^3.8.0`) using the `sqlite3mc` Native Assets build hook**. Because `sqlite3mc`'s documented default cipher is `ChaCha20-Poly1305` (not AES-256), the app explicitly configures **`PRAGMA cipher = 'chacha20'; PRAGMA legacy = 0;`** *before* applying `PRAGMA key`, verifies in **`debug`, `profile`, and `release` builds** that `SELECT sqlite3mc_config('cipher');` / `PRAGMA cipher;` equals `'chacha20'` (failing closed with a `StateError` otherwise), and validates this via a pre-feature Android + Windows proof-of-technology test in Sprint 1.1. Each venue is stored in an isolated `venues/<venue_id>.db` file keyed by OS-protected credential storage (`Android Keystore` / `Windows DPAPI`). | Explicitly locks and verifies `ChaCha20-Poly1305` (256-bit AEAD) across all build modes, guarantees high software performance on budget Android ARM CPUs and Windows `x64`, and enables per-venue cryptographic erasure (`TR-03`, `TR-08`). |
| **`ADR-004`** | **Client/App-Generated UUIDv7 Primary Keys** | All syncable entities use RFC 9562 UUIDv7 generated in Dart (`uuid`) and PHP (`Ramsey\Uuid`). | Time-ordered B-tree locality without offline ID collisions or dependence on PostgreSQL 18's server-only `uuidv7()` (`TR-05`). |
| **`ADR-005`** | **Authoritative 69-Wilaya Trilingual Data-Driven Reference Schema** | `wilayas` (`code VARCHAR(2)` `'01'`..`'69'`) and `communes` (1,541 communes) are seeded from an authoritative, versioned, checksummed dataset verified in Sprint 1.1 against official Algerian *Journal Officiel (JORADP)* / ONS listings in Arabic (`name_ar`), French (`name_fr`), and English (`name_en`). | Corrects the outdated 58-Wilaya assumption in `architecture-gemini-argon.md` and proves completeness via automated count/checksum tests (`TR-12`). |
| **`ADR-006`** | **Strict Separation of `booking_requests` and `reservations`** | Public marketplace inquiries are stored exclusively in `booking_requests` (`pending`, `approved`, `rejected`, `expired`, `cancelled_by_requester`) and never block slots until an owner approves them in an atomic transaction creating a `reservations` row. | Prevents unverified web visitors from locking a venue's calendar and cleanly separates leads from binding contracts (`TR-06`). |
| **`ADR-007`** | **Orthogonal Client `pending_sync` Overlay** | `reservations.status` holds only domain statuses (`confirmed`, `tentative`, `cancelled`, `needs_review`). Client sync state (`has_pending_sync`) is derived from unacknowledged `sync_outbox` rows. | Allows an already-confirmed reservation edited offline to remain `confirmed` while visibly awaiting sync acknowledgement (`TR-07`). |
| **`ADR-008`** | **Configurable Hall Slots & `btree_gist` Exclusion** | Venues define custom `hall_slots` (including overnight ranges where `spans_next_day = true`). `reservations` stores concrete `[starts_at_local, ends_at_local)` timestamps (canonical `'YYYY-MM-DDTHH:mm:ss'` in SQLite) guarded in PostgreSQL by an `EXCLUDE USING gist` constraint where `status IN ('confirmed', 'tentative') AND deleted_at IS NULL`. | Guarantees zero double-bookings across arbitrary slot definitions without denormalized boolean flag drift (`TR-08`). |
| **`ADR-009`** | **Whole-DZD Money, Unconditional `payments` Trigger, `local_actors` & Per-Venue Crypto-Erasure** | All monetary values are **integer whole Algerian Dinars (`BIGINT` `DZD`, column suffix `*_dzd`)**. Recorded `payments` rows carry persistent `local_actors` attribution (`recorded_by_actor_name`, `recorded_by_local_actor_id`, plus `recorded_by_user_id` in Connect) and are protected by SQLite and PostgreSQL `BEFORE UPDATE OR DELETE` triggers that **unconditionally reject all `UPDATE` and `DELETE` operations on every column**. Connect role downgrades and revocations purge restricted local payments by closing and cryptographically erasing the isolated per-venue database file (`venues/<venue_id>.db`) rather than running `DELETE FROM payments`. | Eliminates 100x centime bugs, preserves local actor audit trails across migration, and reconciles strict append-only triggers with Connect cache purging (`TR-10`). |
| **`ADR-010`** | **Monotonic `outbox_seq`, Binary Asset Sync, Auth-First Idempotency & `scanned_through_seq` Cursor** | Client mutations queue in `sync_outbox` ordered by monotonic `outbox_seq` with parent-before-child blocking and binary-before-metadata upload (`PUT /api/v1/sync/assets/{sha256}`). `/api/v1/sync/push` verifies active membership/device/permissions **first** before checking `sync_processed_operations` (bound to `payload_sha256`) and safely strips financial columns on reservation edits by non-financial roles. `/api/v1/sync/pull` uses per-venue `venue_sync_state.last_seq` locked with `SELECT ... FOR UPDATE` at commit and returns `scanned_through_seq` (`MAX(seq)` of the 200-row scanned window) plus `permissions_hash` reset on role change. | Prevents clock-skew bugs, unauthorized idempotency leaks, stalled filtered cursors, and stranded PDFs/logos (`TR-09`). |
| **`ADR-011`** | **Staged Migration with Content-Addressed Asset Verification & Lost-Response Recovery** | Local-to-Connect migration creates a WAL-safe `.walimbak` backup, uploads all 12 relational entity types (including `local_actors`, `contract_templates`, `generated_documents`) to `migration_staging_records`, uploads all binary assets in `migration_assets_manifest` (`generated_document_pdf` and `venue_logo`) to immutable content-addressed S3/R2 paths (`sha256_checksum`) *before* commit, and executes a pure PostgreSQL promotion transaction persisting `status = 'committed'` and `initial_seq` for idempotent lost-response recovery. | Avoids mixing non-transactional S3 moves inside a PostgreSQL transaction and recovers safely if the HTTP `/commit` response drops (`TR-05`). |
| **`ADR-012`** | **Ed25519 Perpetual License, `LicenseSigner` Interface & Safe Connect Expiry** | WalimApp Local uses offline-verifiable Ed25519 `.walimlic` files (`max_venues = 1`, `max_halls = null` by default) signed via a `LicenseSigner` abstraction (`tools/license-issuer` supporting non-exportable hardware/OS-keystore keys or an offline encrypted vault, logging to `issued-licenses.jsonl`). `updates_until` only gates builds compiled after that date. Connect expiry falls back to local offline mode and reconciles `sync_outbox` upon renewal. | Supports hardware-backed non-exportable signing keys and honors perpetual/offline guarantees (`TR-04`). |
| **`ADR-013`** | **Configurable Connect Device Tiers, Mandatory Individual Accounts/RBAC, Price Grandfathering & Lease TTL** | Connect plans (`subscription_plans`) are configurable by Super-Admin (plan names, whole-DZD prices, billing intervals, `max_active_devices`, `max_venues`, `max_users`), seeded with **Basic (`1` active device)** and **Higher-Capacity (`up to 5` active devices at a higher price)**. Individual user accounts (`users`) and venue-scoped RBAC (`venue_memberships`) remain mandatory on all plans (`max_active_devices` is distinct from user seats). Owners/Super-Admins can replace/revoke devices (`device_registrations`). Active `subscriptions` snapshot `agreed_price_dzd` and limits so plan edits never silently alter agreed prices. Offline staff access is bounded by a clock-rollback-resistant 72h `OfflineAccessLease`, and FCM pokes contain zero PII. | Aligns commercial device tiers with multi-user audit/RBAC security and prevents silent price changes or clock-rollback bypass (`TR-11`). |
| **`ADR-014`** | **Trilingual Support (`ar-DZ` RTL, `fr-DZ` LTR, `en` LTR), Optional Per-Language Content & Western Digits** | All three surfaces (`apps/owner`, public marketplace, and Filament Super-Admin) and generated PDFs support **Arabic (`ar-DZ`, RTL)**, **French (`fr-DZ`, LTR)**, and **English (`en`, LTR)** from Day 1, enforcing Western Arabic digits (`0-9`) and integer whole Dinar (`DZD` / `د.ج`). Venue/provider listings require at least one language and resolve missing translations via deterministic fallback (`en -> fr -> ar`, `fr -> ar -> en`, `ar -> fr -> en`) inside `<bdi>` / `Directionality` containers. | Serves Arabic-, French-, and English-speaking users across Algeria and the diaspora without forcing owners to translate every field (`TR-12`). |
| **`ADR-015`** | **Phase 4 Isolation for Virtual Tours & Provider Portal** | 360° virtual tours (`Pannellum` on S3/R2) and provider self-service registration are deferred to Phase 4 while reserving lightweight schema hooks. | Prevents high-bandwidth media and secondary portals from delaying earlier stages (`TR-14`). |
